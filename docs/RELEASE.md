# 公開・復旧手順

[最初のページに戻る](../README.md)

この手順の「公開」は、お客様のサーバー上のWebサイトを入れ替える作業です。
`npm run build` やGitHubへのpushだけでは、本番サイトは変わりません。

## 1. 自分のPCで公開用ファイルを作る

```powershell
npm run generate
npm run build
```

`build` は自動チェックが失敗すると止まります。制限を外して続行せず、表示された原因を確認してください。
成功すると `dist/public-日時/` の場所が表示されます。毎回新しいフォルダが作られます。
その**中身**が今回の公開対象です。古い日時のコピーや、`dist/` 自体は転送しません。

作成後に原本を変更した場合は、もう一度生成・buildしてください。
`dist/` 内のコピーを直接修正すると原本と食い違うので、必ず原本へ戻って直します。

### 公開用コピーに入るもの・入らないもの

| 入る | 入らない |
| --- | --- |
| 全公開HTML、CSS、JavaScript、参照画像 | Gitの履歴・設定（`.git/`） |
| 図面PDF・DXFのZIP | 内部資料、`docs/`、`partials/`、`data/`、テストスクリプト |
| `contact.php` と必要なPHPMailer・ライセンス | 本物のSMTP設定・パスワード・回数制限ファイル |
| `.htaccess` | バックアップ・DBの書き出し・ログ |

`lib/` はPHPが送信処理で使うので、公開用コピーに含まれる分は削除しないでください。

## 2. Gitに保存するもの

編集した原本、共通部品、データ、スクリプトと、生成したHTMLをセットで保存します。
サーバー側でNode.jsを動かさなくても、生成済みHTMLを配信できるようにするためです。

```powershell
git status
git diff
```

差分を確認し、意図した変更だけをコミットしてから、担当者の決めたブランチへpushします。
他の人の未完了の変更や、意味が分からないファイルをまとめて追加しないでください。
`dist/` はGit対象外です。秘密設定を保存するために `.gitignore` を解除しないでください。

## 3. 本番作業を始める前の必須条件

- [ ] 掲載内容と公開日時について先方の承認がある。
- [ ] [引き継ぎ確認票](HANDOVER.md)の担当者と復旧先が決まっている。
- [ ] 現行サイトのファイル・設定・必要なWordPress DBをバックアップした。
- [ ] バックアップを実際に復元できる方法を担当者が把握している。
- [ ] 検証環境でPHP・送信処理・アクセス制限を確認した。
- [ ] [セキュリティ設定](../deployment/SECURITY.md)の本番項目を管理者と確認した。
- [ ] 本番側の現在の配置・WordPress・転送設定を確認した。

未確認なら本番の上書きを止め、先方またはサーバー管理者に確認してください。

## 4. 管理者と配置する

1. 今回作成した公開用コピーの中身を、決められた手順でWeb公開先へ配置します。提示されている公開先は `httpdocs` ですが、現在の設定を管理者に再確認してください。
2. 隠しファイルの `.htaccess` も対象です。ただし**本番の既存ファイルを無条件に上書きしません**。既存のWordPress・転送設定と統合します。
3. SMTPの実際の設定はWeb公開フォルダの外へ配置します。送信元と宛先を混同せず、パスワードは安全な方法で管理します。
4. nginxが直接配信する場合の保護設定、HTTPS、旧URLの転送を確認します。
5. 古いファイルの削除・WordPressの停止・PHPやDNSの変更は、このファイル転送とは別の作業です。承認なしにまとめて実施しません。

## 5. 公開直後に確認する

- トップ、各事業、会社情報、問い合わせ、図面が開ける。
- メニュー・フッターのリンクが正しく、PC・スマートフォンで操作できる。
- 新しいCSS・画像が表示され、ブラウザーの開発者ツールに重大なエラーが出ていない。
- 本番の許可を得たテスト問い合わせが `soumu@bex.co.jp` に届き、返信先が入力した訪問者のアドレスになる。
- 不正入力・連投・送信失敗が成功扱いにならない。
- 内部ファイルが外部から取得できず、HTMLに保護ヘッダーが付いている。
- 旧URLからの転送、HTTPS、サイトマップ、検索向け設定に問題がない。
- 本番に検証環境用の `noindex` やパスワード制限を残していない。

公開日時、コミット、使用した公開用コピー、確認結果を作業記録に残してください。

## 6. 問題が起きたら戻す

表示できない、送信できない、秘密ファイルが見える場合は、追加変更を重ねる前に担当者へ連絡します。

1. 問題と発生時刻を記録し、必要なら公開作業を止めます。パスワード・個人情報をスクリーンショットに含めません。
2. 公開前のバックアップから、今回変更したファイル・設定を承認済みの手順で復元します。Gitのコードだけではサーバー設定や旧サイトの全ファイルは戻りません。
3. DBを変更した場合は、管理者が影響を確認して必要な復旧を行います。変更していないDBを不用意に古い状態へ戻しません。
4. 表示・問い合わせ・アクセス制限を再確認し、先方へ復旧を報告します。
5. 原因をローカルまたは検証環境で調べ、修正・再承認してから再公開します。

認証情報の露出が疑われる場合は、ファイルを消すだけで完了とせず、管理者に失効・変更とログ確認を依頼してください。
